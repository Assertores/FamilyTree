# Warnings about keys before a late "Version" key
## Symptoms
<!-- Must be filled in `Identified` state-->
<!-- Observable signs indicating the presence of the technical debt (e.g., frequent bugs, slow performance). -->
A Person File of another Format Version can produce misleading warnings, e.g. about unknown keys or wrong types, before the warning that its Format Version is not supported, if its "Version" key comes after other keys.

## Context
<!-- Detailed background information, including why the debt was incurred (e.g., rushed deadlines, outdated technologies). -->
The JSON parser of the Library checks the Format Version of a Person File as soon as it reads the "Version" key, and stops reading at a Format Version it does not support ([ADR 0020](../decisions/adr_0020.md)). [REQ 0002](../requirements/req_0002.md) lets "Version" stand anywhere in the object; e.g. [5_Bethany_Barnes/data.json](../../tests/data/example/5_Bethany_Barnes/data.json) has it as the eighth key. The keys before it are read with the rules of the supported Format Version.

Checking the Format Version before everything else would need a first pass over the top-level object that does not use the tokenizer: the tokenizer decodes strings in place, so a second pass would read text that is already decoded ([ADR 0019](../decisions/adr_0019.md)). That is a scanner of its own. A fix would be such a scanner, which finds the top-level "Version" key without decoding, run before the reader.

## Impact
<!-- Must be filled in `Analyzed` state-->
<!-- How the debt affects system performance, scalability, maintainability, etc. -->
Only the Trace is affected: no wrong data is kept, because the file is skipped either way. The template, the Data Entry Tool and 17 of the 18 example files put "Version" first, so the warnings only show up for files written by hand.
